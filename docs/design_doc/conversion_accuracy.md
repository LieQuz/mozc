# 変換精度を上げる

この文書は、このツリーの Mozc で変換精度を上げるときの方針である。辞書の追加と、エンジンのコスト計算の変更の両方を対象にする。語を足すことと、Viterbi が見るコストを変えることは別の問題で、後者を後回しにすると同音語と文節区切りはほとんど動かない。

## 結論

精度の上限は、次の二つで決まっている。

1. 読みが辞書に無い、または複合語として一語で入っていない。
2. パスのコストが品詞の遷移だけを見ている。同じ品詞 ID の同音語は、前後の語が違ってもスコアが動かない。

したがって順番は次のとおりにする。

1. 失敗を「辞書に無い」「ラティスにはあるが 1-best が違う」「文節内の順位だけが違う」に分けて測る。
2. 欠けている語と、区切りを一語に畳める複合語を辞書へ入れる。単語コストは品詞の中央値のままにしない。
3. 品詞遷移に、表層の組 `(左の表記, 右の表記)` のボーナスを足す。これを Viterbi の内側に置く。`CollocationRewriter` のリストを増やすだけでは、文節境界は変わらない。
4. 文節を切る前に、文全体の k-best を語の n-gram で選び直す。
5. ユーザーが確定した組は、予測だけでなく同じボーナス表経由で変換の Viterbi にも入れる。

ニューラルネットワークをラティスの内側には置かない。遅延の予算はミリ秒で、ノード数は文字位置 × 辞書ヒットである。ニューラルモデルを使うならオフラインでボーナス表と複合語へ蒸留し、実行時は今の Viterbi のままにする。

## いまの変換が最適化しているもの

変換の本体は `ImmutableConverter` である。

1. ひらがなキーの各位置で辞書を引き、ノードをラティスに積む。ノードは `key` / `value` / `wcost` / `lid` / `rid` を持つ（`converter/node.h`）。
2. `Connector::GetTransitionCost(rid, lid)` で品詞遷移を足し、Viterbi で最小コストのパスを一本決める（`immutable_converter.cc` の `ViterbiInternal`）。
3. その 1-best を `Segmenter::IsBoundary` で文節に切る。
4. 各文節のスパンだけを `NBestGenerator` が A* で展開する。`Reset(*prev, *(node->next))` の両端は、1-best 上のノードである。
5. `Rewriter` が文節ごとの候補を並べ替え、日付や数値や記号を足す。

コストは次の形である。

```text
path = Σ wcost(node) + Σ transition(left.rid, right.lid)
```

接続行列は `src/data/dictionary_oss/connection_single_column.txt` で、先頭行が `2672`、中身は 2672×2672 の品詞コストである。語の ID は出てこない。

この形で区別できるものと、できないものがある。

| 状況 | 品詞 HMM が使える信号 |
| --- | --- |
| 読みが違う語、品詞が違う同音語 | 遷移コストが変わる |
| 品詞が同じ同音語 | `wcost` の差だけ。文脈は無効 |
| 1-best が切った境界をまたぐ複合語 | 文節候補に現れない。Rewriter からは届かない |
| 直前の確定 | 最後の履歴文節の `rid` だけ。表層は遷移に使わない |

辞書の実数（`dictionary00.txt`–`dictionary09.txt`、2026-09-27 時点）:

| 項目 | 数 |
| --- | --- |
| エントリ | 1,289,076 |
| 異なり読み | 745,965 |
| 複数エントリを持つ読み | 233,183 |
| 表記が複数で、`(lid, rid)` が完全に同一 | 86,710 |
| うち単語コスト差が 0 | 9,191 |
| うち単語コスト差が 1–199 | 5,502 |
| 表記が複数で、品詞が分かれている | 66,192 |

同じ品詞の同音語が 8.7 万読みある。その約 1.5 万はコスト差が 200 未満で、遷移が同じなら実質引き分けである。単語コストのスケールはおおよそ 6000–8000、遷移コストは 0–6000 程度なので、品詞が違う同音語は遷移で十分ひっくり返りうる。品詞が同じ組は、辞書を増やしても順位は動かない。

`src/data/dictionary_oss/evaluation.tsv` は Match / Not Match の既知ケースで、OK 482、FAILED 196 である。文単位の変換精度そのものではない。回帰セットとして使う。

OSS ビルドと Google 日本語入力の差は `docs/about_branding.md` のとおりで、Web 規模の語彙、共起データ、読み訂正、サジェスト抑制がこちら側では薄い。`collocation.txt` は百数十行、`collocation_suppression.txt` はダミー、`suggestion_filter.txt` は実質 1 行である。`reading_correction.tsv` は慣用句の誤読が中心で、タイプミス一般はカバーしない。

## 失敗がどの層で起きるか

手を入れる前に、期待する表記を次のどこで落とすかで分類する。層が違うと直す場所が違う。

1. **OOV**。ラティスにノードが無い。辞書追加でしか直らない。`デコメ` や新しい固有名詞がここに入る。
2. **1-best の敗退**。ノードはあるが、品詞コストの最短路が別の区切りを選ぶ。`折れかかった` が `俺|か|買った` になる類。文節を切ったあとの Rewriter では戻せない。Viterbi のコストを変える。
3. **文節内の順位**。1-best のスパンは正しく、候補リストの 2 位以降に期待表記がある。`CollocationRewriter` や n-best の再スコアで足りる。`思う` / `言う` のようにスパンが一致している同音語がここに入ることが多い。
4. **読みの不一致**。ユーザーのキーと辞書の key が違う。`CorrectionRewriter` と `KeyCorrector` の守備範囲。ラティスにノードが無ければ 1 と同じである。
5. **予測と変換の取り違え**。サジェストは `DictionaryPredictor` と `UserHistoryPredictor`、スペース変換は `ImmutableConverter` である。予測側の `GetLMCost` は文脈付き遷移と BOS 遷移の小さい方を採用する。変換の Viterbi は履歴の `rid` を直接使うが、最後の履歴については `rid = 0` の複製ノードを `wcost = 0` で挿す（`MakeLatticeNodesForHistorySegments`）。文脈を無視する逃げ道が、変換にも予測にもある。

`dictionary_manual` の TSV は、同じ品詞の単語コスト中央値で追加される（`src/data/dictionary_manual/README.md`）。既に本辞書にある語は無視される。中央値では、既存の同音語に勝てない。頻度で勝ちたい語は `aux_dictionary.tsv` の `cost_offset` か、本辞書の `wcost` 自体を書き換える。

`CollocationRewriter` は、隣接文節の候補を上位 12 件、コスト差 3453 以内（`-500 * log(1/1000)`）で見て、共起があれば先頭へ動かす。1-best が別の境界を選んだパスは、この窓に入らない。共起リストの増量は層 3 にだけ効く。

## 測り方

エンジンを触る前に、分類用の評価を足す。既存の `quality_regression` は「期待表記が何位か」までで、層 1 と層 2 を区別しない。

文ごとの TSV を新しく持つ。列は `key`、`expected_value`、`expected_segments`、`domain` とする。`converter_main` と同じ変換 API で、次を記録する。

- 期待表記のノードがラティスにあるか（層 1）
- 1-best の表層を連結したものが期待と一致するか（層 2）
- 文節候補の何位か（層 3）
- 最終的な先頭候補が期待と一致するか

指標は三つに分ける。

- **文一致**。確定結果の連結が期待文と一致する割合。ユーザーがスペース一発で欲しいもの。
- **境界 F1**。期待文節と 1-best の境界がどれだけ一致するか。層 2 の指標。
- **候補内順位**。文節が合っているときの期待表記の順位。層 3 の指標。

`evaluation.tsv` と `src/data/test/quality_regression_test/regression.tsv` は回帰として残す。新しい文セットは学習コーパスと文を共有しない。Wikipedia の見出しで語を足し、同じ記事本文でコストを学習すると、数字だけ良くなる。

予測は変換と別指標にする。先頭サジェストの一致と、確定までのキー打鍵数。ラティスのコストを変えると両方動く。Rewriter だけ変えてもサジェストはほぼ動かない。

## データ側で先に効くこと

C++ を変えずに層 1 と、層 2 の一部が動く。

### 複合語として入れる

品詞 HMM が苦手な区切りは、そのスパンを一ノードにすると最短路がそちらを通りやすくなる。`社員証` のような複合語が OSS 辞書に足されてきたのはこのためである（`dictionary_oss/README.txt`）。

優先する複合語は、評価セットで層 2 になったもののうち、内側の分解より複合語の方が出現が多いものである。人名、組織名、サ変複合（`再起動する`）、助数詞つきは効果が大きい。何でも長く繋ぐと、短い正当な区切りが死ぬ。複合語の `wcost` は、分解したパスのコストより少しだけ小さい値にする。大きくしすぎると、その文字列を含む別の文まで複合語で固定される。

追加先は用途で分ける。

- 品詞が既存の `id.def` にあり、コストは中央値でよい語: `src/data/dictionary_manual/*.tsv`
- 既存語より優先したい語: `aux_dictionary.tsv` の `cost_offset`
- 出したくない語: `dictionary_filter.tsv`

品詞 ID を新設しない。`lid` / `rid` は接続行列、`Segmenter` のビット列、`PosMatcher`、接頭辞・接尾辞ペナルティが共有している。ID を増やすと行列の再構築とセグメント境界データがセットになる。

ライセンスはエントリの出所ごとに分ける。本辞書は IPAdic と沖縄辞書が混ざっている（`dictionary_oss/README.txt`）。NEologd や Sudachi 辞書から語を借りる場合、そのライセンスを辞書ファイル側に残す。上流の `VOCABULARY_POLICY.md` は、個別の語の追加要望を GitHub で議論しない方針である。この作業はローカルの辞書更新として進める。

### 単語コストと接続行列を同じコーパスで取り直す

今の `wcost` と 2672×2672 の遷移は、IPAdic 系の推定に後から語を足したものである。`dictionary_manual` の中央値コストは、その推定の外側にいる。

コーパスを今の辞書で形態素解析し、次を再推定する。

- 単語コスト: その `(key, value, lid, rid)` の頻度。同じ品詞の同音語は、ここでしか分かれない。
- 遷移コスト: `(rid, lid)` の頻度。品詞が違う同音語と、助詞の付き方はここで動く。

出力先は既存のままである。辞書テキストは `key lid rid cost value`、接続は `connection_single_column.txt` の形式で、`data_manager/gen_connection_data.py` がバイナリにする。エンジンのインタフェースは変えない。

コーパスは変換したいドメインに寄せる。一般文なら日本語 Wikipedia とニュース、会話体を上げたいなら字幕や会話コーパスを混ぜる。BCCWJ はカバーは広いがライセンスが別である。再推定のあと `evaluation.tsv` の FAILED が増えていないことを回帰の条件にする。全体の文一致が上がっても、既存の回帰が落ちる変更は入れない。

未知語の単語コストは、品詞ごとの中央値ではなく、その品詞の頻度の下位側（コストが大きい側）に置く。新語を中央値にすると、ありふれた同音語と同じ強さでラティスに出て、短い機能語を食う。

## エンジンに入れる変更

データだけだと、品詞が同じ 8.7 万読みの文脈選択と、1-best が間違えた境界は残る。変更点はコストの中身に限定し、ラティスの形と Viterbi のループは維持する。

### 1. 表層バイグラムを Viterbi の遷移に足す

`ViterbiInternal` はいま次の形である。

```text
cost = lnode->cost + conn.GetTransitionCost(lnode->rid, rnode->lid)
rnode->cost = best + rnode->wcost
```

`CachingConnector` は「遷移は `(rid, lid)` だけで決まる」前提で内側ループをキャッシュしている。表層ボーナスをこのキャッシュの中に入れると、別の表記なのに同じ品詞のノードが同じコストになる。ボーナスはキャッシュの外で足す。

```text
pos_cost = conn.GetTransitionCost(lnode->rid, rnode->lid)
bonus    = lexical.Lookup(lnode->value, rnode->value)  // 未知なら 0
cost     = lnode->cost + pos_cost - bonus
```

`Lookup` は疎な表である。キーは正規化した表記の組、値は非負のボーナス。未知の組は品詞コストだけが残るので、今の挙動がデフォルトになる。ボーナスの上限は遷移コストを 0 未満にしない。

この表が履歴ノードにも効く。履歴の複製は `rid = 0` で品詞文脈を捨てられるが、`value` は元の表記のままである。ボーナスを表記で引くと、品詞文脈を捨てたパスにも「前の語との共起」が残る。

表の中身はオフラインで作る。

- コーパスで隣接した表記対のうち、品詞遷移だけだと負ける対。全部のバイグラムを入れると表が巨大になり、ありふれた助詞まで固定される。
- 既存の `collocation.txt`。実行時の Rewriter からも残してよいが、境界を動かしたい対はこちらに入れる。
- 評価セットの層 2 で、正解パスと 1-best の差がこの対になっているもの。

ボーナスの大きさは、その対を含む文で正解パスと誤りパスのコスト差を測り、差を少し超える値にする。固定値を全対に配ると、短い機能語の組が全体を支配する。

挿入位置は `ImmutableConverter::Viterbi` と、予測用の `PredictionViterbi` の両方である。片側だけだとサジェストと変換が別の語を出す。`NBestGenerator` の遷移も同じ関数を通す。1-best だけボーナス付きで、n-best が素の品詞コストだと、文節内の順位が再びひっくり返る。

### 2. 文節を切る前に文全体の k-best を選び直す

表層ボーナスは観測した対にしか効かない。対が表に無く、品詞コストが複合語を大きく下回るときは、1-best の `prev` が誤りのまま残る。

各ノードは `prev` を一本しか持たない。文全体の代替パスは、Viterbi のあと `NBestGenerator` を BOS から EOS へ一回走らせて取る。今の呼び出しは文節スパンの内側だけである。

手順:

1. いまどおりラティスを作り、品詞 Viterbi で各ノードの前方コストを埋める。
2. BOS から EOS まで A* で k 本取る。k は 8 から 32。品詞コストが 1-best より 3453 以上悪いパスは捨ててよい。Rewriter が既に使っている窓と同じスケールである。
3. k 本を語の n-gram（表記の 3-gram で足りる）で採点し、最良の一本の `prev` を繋ぎ直す。
4. そのパスに対して今の `IsSegmentEndNode` と文節内 n-best を走らせる。

n-gram は KenLM 形式の疎なバイナリでよい。確率そのものを Viterbi コストの単位へ線形に写す。写像の切片は、回帰セットで層 2 が改善し層 3 の既存 OK が落ちない範囲に固定する。

この再選択は変換リクエストに限る。サジェストのたびに文全体の A* を走らせると、キー入力のたびに効いてくる。予測側は表層ボーナス（変更 1）だけにする。

k-best に正解パスが一度も出ない場合は、この段では直らない。そのときは複合語を辞書に足す（層 1 に近い層 2）。

### 3. 確定履歴を同じボーナス表へ入れる

`UserHistoryPredictor` は予測では強い。変換の `Predictor::Convert` は履歴候補を返すだけで、Viterbi の 1-best は変えない。`UserSegmentHistoryRewriter` は切ったあとの文節候補を LRU で並べ替えるので、層 3 にしか効かない。

確定時に `(前の表記, 確定した表記)` をメモリ上のボーナス表へ足す。変更 1 と同じ `Lookup` を見る。これで次の変換から区切り自体がユーザーの確定に寄る。

腐るのを防ぐ条件:

- 表示されただけでは足さない。ユーザーが選んで確定した組だけ足す。
- ボーナスは回数の対数で増やし、上限をコーパス由来のボーナスと同じにする。一度の誤確定でシステム辞書を上書きしない。
- 既存の履歴クリア (`ClearAllHistory`) でこの表も消す。

### 4. 読みのゆれはラティスのノードとして競わせる

`reading_correction.tsv` は既知の誤読を `CorrectionRewriter` が後段で直す。`KeyCorrector` は訂正キーにペナルティを乗せるが、対象は限られる。

タイプ由来のゆれ（長音、促音、`は`/`わ`、隣接キー）は、訂正キーのノードを元キーのノードと並べ、`wcost` に一定のペナルティを足して Viterbi に選ばせる。後段の Rewriter だと、誤った読みの 1-best が別境界を取ったときに届かない。ペナルティは「そのままで辞書にある語」が勝つ大きさにする。ペナルティが小さいと、正しい短い語が誤訂正に食われる。

## 入れないもの

- **接続行列を語 ID の密行列に置き換えない。** 異なり表記は辞書規模で、Viterbi の内側ループが品詞 ID のキャッシュを前提にしている。疎なボーナスが同じ情報を小さいコストで持つ。
- **Transformer を文字入力のたびに呼ばない。** 変換キーを押したときの k 本の再スコアなら遅延に収まる可能性があるが、まず 3-gram で層 2 がどれだけ残るかを見る。残ったものだけ蒸留する。
- **品詞 ID の増設で語を分けない。** 同音語を別品詞にして遷移で分離すると、`id.def` と行列とセグメント境界の三点が同時に壊れる。表記ボーナスの方が局所的である。
- **共起テキストだけ増やして終わらない。** `collocation.txt` は層 3 の並べ替えである。評価で層 2 と出た対は、変更 1 の表へ入れる。

## 実装の順

各段の完了条件は、新しい文セットの文一致が上がり、`evaluation.tsv` の FAILED が増えないことである。

1. **計測。** ラティス在籍、1-best 一致、文節内順位を出すドライバを `converter/quality_regression_util` の隣に置く。エンジンの挙動は変えない。ここで層の内訳が出てから辞書とコストのどちらに工数を割るかを確定する。
2. **辞書。** 層 1 の語と、層 2 のうち複合語にできるものを `dictionary_manual` と `aux_dictionary.tsv` へ入れる。`wcost` は分解パスより少し小さい値。中央値のままにしない。
3. **コストの再推定。** 同じコーパスで `wcost` と `connection_single_column.txt` を作り直す。C++ は変えない。品詞が違う同音語と助詞接続がここまでで動く。
4. **表層ボーナス。** `Viterbi` と `PredictionViterbi` と `NBestGenerator` の遷移に、キャッシュの外からボーナスを足す。データは疎な表記対。回帰が落ちた対は表から外す。
5. **文全体の k-best。** 変換リクエストだけ、BOS–EOS の A* のあと 3-gram でパスを一本に決めてから文節を切る。
6. **確定履歴。** 変更 4 の表へ、確定された表記対だけを実行時に足す。

4 までで変換とサジェストの両方の 1-best が動く。5 は変換の境界専用、6 は個人化である。5 と 6 は 4 の計測を見て、層 2 が残っているときだけ着手する。
